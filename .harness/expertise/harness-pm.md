# Expertise — harness-pm
## Patterns (max 15)
- P-01: WHEN a criterion protects objects selected in one role DO grade protection by identity across every role and indirect writer; require overlapping-role counterexamples, not only disjoint fixtures or inspection of the opt-in branch.
- P-02: WHEN a criterion will cite automated evidence from a test kind DO check that kind's detect globs match files on the surface being changed: a non-null runner matching zero files here is a gate that proves nothing. Widen the runner as a task rather than downgrading the criterion to inspection.
- P-03: WHEN a grading set is derived from the material under grading — the plan's own file lists, or whichever producers a corpus happens to contain — DO re-base it on the declared contract that material cannot define, then name the case that now fails.
- P-04: WHEN a criterion quantifies over N items DO give each item its own assertion, in the verify you author and again when grading. A file-global search or a matching count is satisfied by the conformers alone, blind to the one item that conforms to nothing.
- P-05: WHEN goal-checking DO grade each criterion only from evidence discriminating its exact clauses, independent of QA or process-gate status; if all criteria pass but another gate fails or conflicts, preserve SC verdicts and block validation separately without inventing a product finding before a concrete failure scenario is known.
- P-06: WHEN closing a prior finding DO directly re-measure its failed premise at the current pin, then distinguish implementation repair from authority change: fixed means the scenario no longer occurs under the same contract; resolved by signed amendment means approval changed that contract. A generic green suite proves neither.
- P-07: WHEN you write an ordering argument for a removal or migration sequence DO enumerate every gate that reads the changed surfaces and say what each does in each intermediate state. A one-gate argument reads as rigorous and is not; a missed second gate reddens the whole suite.
- P-08: WHEN you author a task's verify DO run it against the state the task's own intent predicts at completion, and against the intent prose itself: an ALL-PASSED assertion is unsatisfiable where the intent predicts a case still fails, and the remedy is a task boundary, not verify text.
- P-11: WHEN a criterion quantifies over a scope DO check, before dispatch, that the tasks tracing to it carry file lists covering that scope. A task naming one file cannot satisfy a clause over every document, so the criterion fails at goal-check for a planning reason no retry can fix.
- P-12: WHEN a task turns an explicitly unresolved operator-facing contract into implementation requirements DO retain only the settled contract or obtain the missing ruling before signature; otherwise the plan silently chooses an observable behavior the operator reserved.
- P-13: WHEN judging whether a criterion is covered DO count independent methods, not clauses or concurring readers. Checks sharing one method share one blind spot, and a second reader who repeats that method is one measurement counted twice. Give at least one clause a behavioural check.
- P-14: WHEN planning a semantics-preserving refactor DO record baseline exit, stdout, and stderr receipts for every suite that owns the observable contract; permit only enumerated, bounded divergences, each with a red-first proof and an explicit ruling.
- P-16: WHEN a plan deletes or changes behaviour, or every criterion passes, DO grade the affirmative present-tense claims in signed prose against measured behaviour: the plan's text and each kept decision's whole entry, not only its policy clause. No criterion quantifies over them, so an overclaim survives panels and goal-checks.
- P-18: WHEN a criterion declares what counts as valid or absent in an external payload DO enumerate every field the decision reads, plus the identity binding of related objects, in the criterion and again as per-field graded evidence; container-shape cases alone let each later round surface one more unvalidated field.
- P-19: WHEN declaring a defect class closed DO run one probe one boundary beyond the stated class contract (an adjacent route, configuration or caller) and state that boundary in the claim. Measured only inside its contract, closed is true by definition while the next round finds the neighbour.
## Gotchas (max 15)
- G-01: WHEN citing or counting anything in a file another agent may be editing DO pin the figure with `git grep <SHA>` and re-read the anchor at final state. Working-tree numbers mix pre- and post-edit positions, and equal counts across a concurrent edit are not confirmation.
- G-02: WHEN resolving which lane may write a path DO run the domain guard on EVERY path the plan names, never a sample, and read its exit code. The team config gave the wrong lane where the live hook gave the right one, and a sample says nothing about the rest.
- G-06: WHEN a path or input predicate is contractual DO specify whether it classifies raw or normalized input and require cases where normalization changes category. Preserve the original-entry passthrough rule separately; trimming or unquoting before classification can invalidate an otherwise matching predicate.
- G-08: WHEN citing a suite's exit code or ok-line count as proof it passed DO read the runner's failure accounting first. One counting a failure only when a detail string is non-empty exits 0 while printing FAIL lines, which no ok-count sees. Grep the failure prefix.
- G-09: WHEN a criterion grades the cumulative change set DO place its gate in the terminal task after every successor that can invalidate it, regardless of file-list overlap; an early pass is stale evidence.
- G-10: WHEN a check compares a field looked up by a name discovered at runtime DO add an explicit key-absent branch reporting CANNOT VERIFY. A wrong key makes both sides None, the comparison reports clean for every record, and its silence reads as proof.
- G-13: WHEN you narrow, correct or supersede a claim DO fix every occurrence of it in the same edit — grep the whole artifact, and rewrite the artifact itself whenever your handoff summary supersedes it. The summary reaches one tier; the file is what the next context opens.
- G-14: WHEN a verify asserts absence by counting DO NOT wrap the search in `test "$(cmd | wc -l)" = 0`: a search that errors prints nothing, the count is zero and the test passes. Assert the search's exit status, or pair it with a positive control that must match.
- G-15: WHEN you author a verify, or grade a criterion, over a file the task produces DO read it at the ref under review, never the working tree. A tree-reading check passes for any deliverable that was never committed, and untracked output leaves no evidence at the ref at all.
- G-16: WHEN a criterion's command defaults to a path inside the feature worktree DO state the owner-root override inside the criterion: the worktree does not outlive the branch, so a post-merge re-run reads as unrunnable rather than red, and the criterion can never be re-verified.
- G-18: WHEN execution uses an installed or bundled runtime DO record invocation-time launcher path, version and executable hash separately from source-suite checkout and release-tag metadata. Source provenance cannot identify the binary that actually ran; label unmeasured identity rather than infer equivalence.
- G-19: WHEN adopting execution from another commit DO bind the executed subjects to the review pin by comparing source, tests, configuration, fixtures and probe; obtain fresh evidence for mutable external populations. Keep the executed commit explicit: unchanged subjects permit evidence transfer, not a claim of re-execution.
- G-20: WHEN authoring a standalone verify DO specify inherited environment isolation, clone-local configuration and required ref targets alongside commit identity before dispatch; a fresh clone neither sanitizes the parent environment nor preserves local Git setup, so correct checkout identity alone cannot establish the intended execution context.
- G-21: WHEN a writer's stdout is the evidence of what it did DO capture it whole into a durable path inside your write grant as it runs: a temp file vanishes and printed prefixes truncate, and re-running a writer to recover it records a different run.
- G-22: WHEN a criterion promises every invocation converges, recovers or checks something DO trace each entry path to where that mechanism runs: a preflight that refuses before reaching the shared core skips it, so a re-run never converges. Grade per entry path, not by the core alone.
## Outcomes (max 10)
- O-01: WHEN proving a test reddens if either side changes alone DO mutate one branch at a time, never one per side. Separate branches behind the same rendering redden different assertion sets, so a per-side proof reports the side covered while a whole branch stays unprobed.
- O-02: WHEN a criterion's discrimination rests on one fixture fragment DO delete that fragment and re-run: a suite that stays green means the property is proven but undefended. Grade MET on the criterion's own words and route the fragility as a backlog chore, never as a new gate.
- O-04: WHEN proving a NEW conjunct of an and-chained verify can turn green DO build a temp tree where every earlier conjunct passes, then mutate only the new one. On the pre-change tree an earlier conjunct exits first, so the new one never runs and its green is assumed, never observed.
- O-06: WHEN a probe or mutation harness reports a uniform verdict across cases DO assert it ran the real artifact and reached the branch under test. A mis-invoked harness, or a call with the wrong argument shape, returns one early guard's answer for every case and reads as clean.
- O-07: WHEN a criterion claims a check fails against the pre-change code DO run the current suite against the earlier commit's copy of the changed file. Where the change is one script, a prior commit is a free mutant and proves the clause independently of the gate that asserted it.
- O-08: WHEN proving a set of in-file self-test cases discriminates DO patch one collaborator at a time, record which cases redden under each, and assert no case is ever-green. A per-probe pass rate hides a case nothing can falsify.
- O-11: WHEN authoring a proof that a gate can fail DO reuse the red idiom the target's own tests already use, never a relative commit ref: the predecessor task lands as its own commit, so the ref drifts and the case reads the post-change file.
- O-12: WHEN proving a verify block verbatim without touching the file under test DO build a temp root whose data directories are symlinks and whose script is a real COPY: python resolves a symlinked script for sys.path[0], so sibling imports vanish and the run dies in a dependency-missing branch.
- O-13: WHEN proving a verify is red on the unbuilt tree DO read where the red arises, not the status: a missing argument exits 2, a diff over a self-edited file is red while uncommitted, and an earlier failure point reddens before the one the task names. Each mimics discrimination.
- O-14: WHEN several interfaces share a helper DO distinguish inspected generalization from executed coverage: identify which predicate-by-interface combinations have dedicated assertions, which are inferred through the helper, and which lack evidence. Shared implementation does not prove every combination was tested.
