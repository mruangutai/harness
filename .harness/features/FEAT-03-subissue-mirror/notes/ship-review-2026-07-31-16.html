What the feature actually does now

Harness mirrors each feature's plan into GitHub Issues. Before this feature, that mirror was wrong in three ways that would have quietly corrupted your issue tracker the first time you turned it on.

1. Absorbed issues were being closed. When a task "absorbs" an existing backlog issue, it means the task is part of that issue — not a replacement for it. The old code closed the absorbed issue when the task finished, which would have closed live backlog items that were only partly done. Now absorbs: is a citation and nothing more. It closes nothing.

2. There was no way to abandon a feature. If you dropped a feature, its GitHub issues stayed open forever, or you closed them as though the work had shipped. There is now an abandon path that closes the feature's own issues as not_planned — the state that says "we decided not to", not "we finished".

3. Shipping or abandoning could close an issue that was never ours. This is the subtle one, and it is the reason this feature went through three rounds of revision before you signed it. A feature's "parent" issue is sometimes one harness created to hold the feature's tasks, and sometimes one you already had in your backlog that the feature adopted. Closing the first kind is correct. Closing the second kind asserts something false about your own live work — and completed is exactly as false as not_planned when the thing isn't yours.

So the parent's fate now follows its recorded origin: harness closes what it created, and leaves alone what it adopted or cannot prove it created. When in doubt, it leaves your issue open. The milestone closes either way, because that one is always harness's own.

There is also housekeeping worth one line: the project's unit test gate was not running the tests that matter. Its file pattern matched zero files in this repo, so eight criteria claiming "verified by unit tests" rested on a gate that did nothing. That is fixed and the gate now runs three test scripts.

Your one judgement call (not a defect)

An abandonment can stop halfway through and still report success.

If the network or GitHub fails partway through abandon — specifically while posting the reason comment — the tool exits 0 having closed no issues and no milestone. Nothing records that it half-happened.

This is not a bug against anything you approved: the rule is "an environmental failure exits 0 with a SKIP line", and this obeys it literally. But the spirit is that a skip means "did nothing", and here it can mean "did some of it".

Product's recommendation, which I endorse: do not fix it inside this feature. It is a new requirement, not a missed one — making a terminal state atomic is real design work, and it belongs with the follow-on feature already sketched. Your call: accept it as a known limitation, or scope it now.
