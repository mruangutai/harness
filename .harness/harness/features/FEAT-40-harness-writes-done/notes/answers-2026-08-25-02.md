## Q6 — AT SHIP ONLY. Not per commit, not per station write.

The audit runs **once per feature, inside `ship`**, and nowhere else.

The reasoning, so it is not re-litigated: `ship` already reads GitHub for the open-child check under
the new sixth read-back purpose, so the audit's four calls (`board_lifecycle.py:831`, "Call 3/4") are
a small increment on a read that is already happening — rather than four calls on every commit
forever, or four on every station write.

The accepted cost, named: **a card closed outside the harness can sit wrong for the whole build**
and is only caught at ship. That is tolerable because ship is the moment the wrongness would
otherwise cause harm — it is where the open-child decision is made.

Rejected explicitly: running it at each station write. The leak happens when the harness is **not**
writing a station — a human closing an issue in the web UI triggers nothing — so a station-change
trigger catches it no sooner in practice, at several times the cost.

**Plan change: REQ-06's compensating control is the audit, scheduled inside `ship`.** Update the
task that owns `ship` and REQ-06's narrowing note.

## Q8 — DELETE `close-task`.

Remove the subcommand from `gh-sync.py`, its tests, and every reference in the docs the plan already
audits — `references/github-mirror.md` names it at `:30`.

The reasoning: it is a harness command that closes an issue while bypassing the station, so it can
produce the exact state this whole feature exists to prevent — an issue CLOSED with its card NOT at
`Done`. Keeping it would leave a harness-blessed route around the rule the feature installs.

Note the interaction, so the plan is consistent: the new Bash gate refuses a **typed**
`gh issue close` but is structurally blind to a Python subprocess, so the gate would NOT have stopped
`close-task`. Deleting it is what stops it. After this, **`abandon` is the only harness command that
closes an issue directly**, and that is the one narrow exception the decision records.

**Plan change: a task deletes `close-task`.** pm decides whether that is a new task or folds into an
existing one, and states its reasoning either way. It is not the ticket's original scope, and the
operator has ruled it in.
