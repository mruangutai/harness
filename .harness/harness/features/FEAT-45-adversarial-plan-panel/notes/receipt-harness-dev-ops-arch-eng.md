## Q2 — is the lead-side wrapper sound

**Mechanism.** `SubagentStop` fires on **every** subagent's stop, harness or not — registered once, no agent matcher (`merge-settings.py:77-82`, "No agent matcher: one registration serves all 16, and the script passes through anything that is not a harness agent"). Inside `validate-digest.py:900-907`, a present non-`harness-`-prefixed `agent_type` returns 0 immediately — **the reader's own return is never validated, structurally, by anything, at any point.** What gets validated is the **lead's own** stop event: `harness-validator-lead`'s digest schema (`validate-digest.py:204-206`, persona `"lead"`) requires `team`, `steps_run`, `cycles_used`, `members` (non-empty list if `steps_run>0`, line 737-741), `must_fix`, `branch`, `escalations`, `sc_status`, and the roll-up check (`:743-759`) walks `members` entries for a `verdict:` key only — **not** `severity`. So "normalize" concretely means: the lead writes its own digest (shape enforced on ITS `SubagentStop`), inside which it authors a `members:` entry summarizing the reader by transcription. **Coverage gap named precisely**: the reader's raw JSON shape, and whether the lead's transcription is a faithful summary of it, are both **unvalidated** — no script checks either.

**Shape vs. content line, and whether it is structurally required.** `harness-validator-lead.md:85` ("`must_fix` non-empty **or** `severity_max >= high` → FAIL") makes `severity_max` load-bearing for the gate computation, but `validate-digest.py`'s `"lead"` schema does **not** require `severity_max` as a field (absent from the tuple at line 204-206) — so nothing mechanically forces the lead to have a real number to reconcile from. For the four existing harness reviewers, this is closed today: schema `"reviewer"` (line 191) **requires** `severity_max`/`findings`/`must_fix` — so those four members structurally hand the lead a severity to transcribe, never one it must invent. The panel's non-harness reader carries **no such schema**, because non-harness personas are exempt (`validate-digest.py:906`). **Concrete, implementable answer**: the reader's own prompt/contract (authored by `harness-pm` under REQ-05) must require the reader's raw JSON to include its own `severity` per finding (e.g. `{finding, severity: low|med|high|critical, ...}` — mirror the `"reviewer"` schema's field name so the lead's "reconcile severity" step (`harness-validator-lead.md:75-76`, already-existing prose for the four reviewers) extends verbatim to a fifth source instead of inventing a sixth rule). Absent that contractual requirement, the lead is structurally forced to invent `severity_max` from unstructured prose — which is exactly the hazard the question names, and nothing today prevents it.

## Q3 — deadlock paths surviving the override

**a. Reader returns HIGH on every plan (non-convergence).** The generic team `on_fail`/`loop_back` mechanism already exists and bounds this: `harness-team/SKILL.md:154-165` — `max_cycles` per step, and at the cap, `then: escalate` or `then: halt` (not an infinite loop by construction). **This is not a new mechanism the panel needs; it is the standing team-runner contract already applied to every step.** Carry required: `harness-pm`'s `plan.yaml` step definition for the panel readers must set `on_fail: loop_back` with an explicit `max_cycles` and `then: escalate` (never `then: halt` silently, which would strand the plan with no route up) — this is a plan-authoring choice, not a new mechanism to build.

**b. Override needs a signature the gate is blocking (circularity).** Traced the actual gate surface: `.claude/commands/harness-plan.md:21-26` — the **terminus** is "ONE approval, taken by you [main session]"; nothing in this prose, nor in `check-state.sh:158-164`, nor in `check-plan-routes.py`, mechanically **blocks** the write of `plan.yaml approval:`. `check-domain.sh:164,300-310,540-544` — the main session carries no `agent_type` and is **exempt from every domain gate by mechanism**, not by a conditional the panel's HIGH finding could trip. So: **there is no real circularity** — the "gate" that stops presentation is prose/procedural (the orchestrator's own playbook withholding the ask), never a file-level lock, and the main session can write `approval:` at any time regardless of finding severity. Carry required: state this explicitly in the plan design so nobody later "fixes" it by adding a mechanical block that WOULD introduce the circularity that doesn't exist today.

**c. Re-run's new finding arrives after an override was recorded (staleness/ordering).** This is the one real gap. Nothing on disk today gives a panel finding an **identity** stable across runs — `plan.yaml` has no JSON schema (confirmed: `.claude/skills/harness/bin/*schema*` contains only `feature-schema.json`/`feature_schema.py`, which govern `feature.json`, not `plan.yaml`), so an override recorded against "finding X" has nothing to bind to except free-text matching. BRIEF REQ-13 ("a re-run does not overwrite the prior run's record") requires each panel run to land at a **run-scoped path** (mirroring `runs/*-validator/**`, cited in the BRIEF's own decision list) so cycle *N*'s findings never overwrite cycle *N-1*'s — but a stable **finding identity** (e.g. a content hash or `id:` per finding, carried from run to run) is a separate carry the BRIEF does not yet name and `harness-pm` must add: without it, an overrule recorded against run 1's wording cannot be mechanically checked against run 2's re-phrasing of the same finding, and REQ-08's "distinguishable... from the record alone" degrades to prose matching.

## Q4 — where the overrule record lands

**Grants.** `.harness/team-config.yaml:17-26` (`main_session.writes`) already lists `".harness/*/features/*/plan.yaml approval:"` as a whole-key YAML fragment grant. `check-domain.sh:580-593` (`approval_guard`) resolves that fragment via `_yaml_key_range`, which captures the **entire `approval:` mapping block**, sub-keys included — confirmed by the fnmatch/key-range logic at `:574-593`. A `rulings:` sibling under `approval:` is therefore **already inside** the existing grant; no `main_session.writes` edit needed. This is corroborated independently: `feature_schema.py:59-63`'s `_REDIRECT` string — printed whenever a stray key is rejected from `feature.json` — **already tells the rejected writer** "An operator ruling goes in that feature's plan.yaml under `approval.rulings`", i.e. this destination is a naming convention this codebase already anticipates, pre-FEAT-45.

**Schema.** No JSON schema governs `plan.yaml` at all — only `feature-schema.json` exists (`.claude/skills/harness/bin/*schema*` glob), and it governs `feature.json` (`feature_schema.py:2-3`, DEC-191's closed `additionalProperties: false` state schema). `plan.yaml`'s `approval:` is read today only by `check-state.sh:159-164` via `doc.get("approval")` / `.get("status")` — an **open** mapping; adding `.rulings` breaks nothing there and needs no validator change. `DEC-174`'s `main-session-direct` carve-out (hooks/validators/gate scripts) is therefore **not triggered** by candidate (i) — no hook, validator or gate script needs editing to add a sibling key nobody currently reads defensively.

**Grading against REQ-08/09/10.**
- (i) `approval.rulings`: REQ-08 — machine-distinguishable from a resolved finding by construction (a `status: overruled` entry with `who`/`when` fields, sibling to but never replacing the finding's own resolved-or-not state); REQ-09 — **zero grant cost** (shown above); REQ-10 — machine-checkable the same way `check-state.sh:159-164` already checks `approval.status`: a new read of `approval.rulings` presence/shape, symmetric with the existing pattern, no new mechanism class.
- (ii) `notes/answers-*.md`: REQ-09 — already granted to the orchestrator per DEC-44, no widening either; but it is **free-form prose** by design (DEC-44's whole point is "the user's answers", conversational) — REQ-08's "from the record alone" and REQ-10's "detectable by machine" both degrade to text-pattern matching against prose that was never designed to be parsed, and nothing today parses `notes/answers-*.md` as structured data at all. It would be strictly worse at REQ-08/REQ-10 and gains nothing (ii) has that (i) lacks.

**Recommend (i).** What (ii) would have been better at: nothing measured — it is the DEC-44-blessed home for *conversational* Q&A, which is a different kind of record than a structured, machine-checked ruling; forcing the ruling into it would be re-purposing a channel designed for narrative, not adding a genuine strength.
