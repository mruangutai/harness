## Ruling 1 — sub-issues stop closing at commit

**The conflict.** The operator had already ruled that when all sub-issues finish `Building`, the
parent AND the sub-issues move to `Review`, then to `Done` once the panel's feedback is resolved.
The plan's step 6 runs `gh-sync close-task` as each commit lands, and GitHub moves a closed card
straight to `Done`. A sub-issue cannot hold `Review` if it is already closed. The two could not
both stand.

**The ruling: stop closing sub-issues at commit.** `close-task` no longer runs per-commit.
Sub-issues stay OPEN through `Review` and close with the parent at merge.

**What this overturns.** The BRIEF's inference 3 — "`Review` is a PARENT-only station, sub-issues
run `Ready` → `Building` → `Done`" — is REJECTED. Sub-issues do reach `Review`.

**The cost the operator accepted, stated when the ruling was taken.** This returns to FEAT-31's
close-everything-at-merge shape, which the step-6 ruling had been written to replace. The stated
reason step 6 existed was that closing everything at merge is why board 3 has never had a card at
`Review`. Under this ruling the stations are written explicitly instead of falling out of the close,
so `Review` becomes reachable for a different reason than step 6 aimed at.

**Surfaces that must change:** the BRIEF's inference block, step 6, `T-13`, `T-15`, `T-19`, `T-20`,
REQ-08 and REQ-10 all rest on this and were drafted the other way.

## Ruling 4 — INV-26 is widened; the sub-issue's CARD reads `Review` while its ISSUE stays OPEN

**The operator ruled: fix the gate. T-22, D-24 and SC-20 are accepted.** Ruling 1 stands exactly as
given and is not reopened.

**Two words had been blurring and the ruling separates them.** An issue's STATE is GitHub's own
field, `open` or `closed`, two values. A card's STATION is the board column, six values. The
lifecycle the operator confirmed:

| Moment | Card station | Issue state |
| --- | --- | --- |
| Plan signed | `Ready` | open |
| Work underway | `Building` | open |
| All sub-issues done building | **`Review`** | **open** |
| Panel feedback resolved, merge | `Done` | closed |

**Why the issue must stay OPEN is mechanical, not stylistic.** GitHub's `Item closed` workflow moves
a closed issue's card to `Done` on its own. Close a sub-issue at commit and the card jumps to `Done`
within seconds, so `Review` is never observable. That is the measured reason board 3 has never held
a card at `Review`.

**INV-26's defect is that it never learned this.** It assumes plan `done` implies the issue is closed
implies the card reads `Done`. T-22 teaches it the bold row: plan `done` + issue OPEN + card
`Review` is CORRECT, not a violation. Without it the pre-commit gate reports every done task of
every in-flight feature as a violation, which is how a gate stops being read.

**The cost, accepted with the ruling: SC-10 goes from five untouched gate files to four.** That is a
promise changing, not a behaviour. T-22 is `main-session-direct` under DEC-174 — the harness plans
its own enforcement work and does not execute it through the team.
