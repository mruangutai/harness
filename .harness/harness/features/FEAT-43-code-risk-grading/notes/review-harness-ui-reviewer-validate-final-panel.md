# FEAT-43 final pinned UI review

**FAIL.** In scope: the CLI text/JSON report is the only user-facing surface this feature ships, and
it fails the BRIEF's own Definition-of-Done bullet on actionable rejection messages. A gated
grade-3 production function — the design bar this feature itself defines and unit-tests (SC-17) —
gets no severity marker in either the text or JSON report and is never named in the shipped
code-review guidance, so a reviewer or author following the guidance verbatim cannot discover that
it blocks without reading the tool's source. Six such records exist in this exact diff.

## Finding — high, must_fix

**F-UI-01 — grade-3 gated production failures carry no blocking signal, and the shipped guidance
never names them.**

`code-grade.py:110-122` (`_text`) prints `SEVERITY: high` for every grade-1 record and
`REASON REQUIRED: <name>` for every grade-2 record, but nothing at all for grade-3 records — the
`_record` severity map (`code-grade.py:53`) is `{1: "high", 2: "med"}.get(grade.grade)`, which
returns `None` for grade 3. The JSON form carries the same gap: `"severity": null`. Yet
`_status` (`code-grade.py:157-159`) — `1 if any(record["grade"] < record["bar"] and record["grade"]
!= 2 …)` — treats a gated grade-3 production function exactly like grade-1 for exit-code purposes:
both cause exit 1, only grade-2 is carved out. BRIEF's own SC-17 requires this ("a production
function at grade 4 passes and at grade 3 fails"), so grade-3-blocks is correct policy — the defect
is that nothing in the message says so.

`harness-code-review/SKILL.md:58-64`, the guidance this feature ships for the reviewer who consumes
this output, instructs: "For every gated grade-1 function, record a **high** finding … For every
gated grade-2 function, record a **med** finding …" — grade-3 is never mentioned in that section or
anywhere else in the file (checked with a full-file grep for `FAIL`/`bar`).

**Concrete failure scenario, reproduced live on the pinned range:**

```
python3 .claude/skills/harness/bin/code-grade.py \
  --base 7ccfae8dd7644bc3aaea612dabf4317c0d804f99 --head 94383e671e51f95d142f3220f97c8e453721d516
```
exits 1, 98 records, 98 PASSING-eligible minus 21 below-bar (15 grade-2, 6 grade-3, 0 grade-1). The
six grade-3 production FAILs, none carrying `SEVERITY` or any other blocking marker:

- `check-plan-routes.py:91 resolution_manifest` — cyc 8 / cog 11 / ABC 22.0, driver `cognitive+abc`
- `code-grade.py:80 _diff_paths` — cyc/cog/ABC driver `cognitive`
- `code_grade.py:232 _records.collect` — driver `cognitive`
- `code_grade.py:318 _changed_python_files` — driver `cognitive`
- `gate_policy.py:33 load_policy` — driver `cognitive`
- `gate_policy.py:75 evaluate_qa` — driver `cognitive`

A reviewer following `harness-code-review/SKILL.md` to the letter, or an author scanning stdout for
`SEVERITY:`/`REASON REQUIRED:` lines the way the guidance trains them to, will not raise a finding
for any of these six — even though the tool's own exit status already failed the build on their
account. Discovering that a grade-3 record blocks requires reading `_status()` in
`code-grade.py`'s source, which is precisely what the BRIEF forbids: "without opening the tool's
source or guessing." This is not hypothetical — it is the live state of the pinned diff under
review, and it is a fresh regression surface of the very fix that closed the feature's earlier
"exit 1 for any below-bar record including grade 2" defect (recorded in
`notes/review-harness-code-reviewer-validate-review-final-validator.md:66`): carving grade-2 out of
`_status`'s blocking condition left grade-3 sharing grade-1's blocking behavior with none of
grade-1's visible signal.

Severity: **high** — wrong behaviour in a realistic case (harness-code-review's own severity table),
proven on the actual pinned diff, not a hypothetical. It gates: `must_fix` non-empty.

## What was not found wrong

The rest of the report is sound: `PATH`/`LINE`/`QUALNAME` on every record; `DRIVER` correctly names
which of the three metrics is worst; `COGNITIVE` is labelled "(Sonar-style approximation)" on every
record; paths are `json.dumps`-escaped so odd filenames render safely; sort order is
`(path, line)`, stable and deterministic; `UNGRADED:` names files by path when parsing fails. No
colour-only signalling, no focus/hit-target/theme surface exists for a stdout stream, so those
dimensions are not applicable here. Source audit cannot verify terminal line-wrapping at real
widths — a human/UAT check would be needed for that dimension, but it does not change the verdict.
