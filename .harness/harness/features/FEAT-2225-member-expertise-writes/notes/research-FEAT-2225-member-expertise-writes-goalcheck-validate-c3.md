## Two receipt-design boundaries

**1. Explicit base → merge-base: acceptable for close-chain provenance; not a current-main replay substitute.** `authorized_base` resolves the supplied SHA and computes `merge-base(base, HEAD)` (`expertise-merge.py:1573-1581`). For `A → feature H` and independent `A → main M`, it anchors at A, not M. This preserves the historical write chain while original-persona supersession reconstructs against exact M (`_supersession_context:1336-1346`, `_reconstruct:1349-1356`); the batch records the actual pre-write hash (`_land_target:1370-1377`). Existing controls explicitly verify the replacement with and without `--base`, then retain withdrawal/history/idempotence. Replay still uses the exact supplied M, not its merge-base (`replay_feature:1272-1286`), as SC-04/05 require. A nonancestor explicit base with shared history is intentionally supported, not an automatic refusal. An unrelated base fails merge-base with exit 15; an invalid/unresolved SHA fails `resolve_base:990-997` with exit 15 and **BASE UNRESOLVED**, not necessarily NO AUTHORIZED BASE. No new finding for this design.

**2. Default branch → HEAD self-anchor: unacceptable under SC-03/T-04's unconditional close boundary. The new unit control actually asserts origin/HEAD at feature HEAD wins over older local main (`test-expertise-ops.py:780-788`). Therefore the fix receipt's “HEAD is never an anchor” and “only the main checkout” claims do not follow from the implementation.
