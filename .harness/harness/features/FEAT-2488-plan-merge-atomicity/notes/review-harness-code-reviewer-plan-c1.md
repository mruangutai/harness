# FEAT-2488 — plan scope and architecture review

**FAIL pending plan revisions.** Keep the plan lane and two main-session-direct tasks. A byte-image journal is a good fit for process-interruption recovery, but the draft does not bind replay to the journal currently under lock or keep transaction outcome reporting in the core.

1. **High · substance · T-01 (SC-01 / D-01 / D-02): replay can act on an old journal.** At `plan.yaml:85–87`, A reads J1 before locking; B completes J1, publishes J2 and dies after replacing the plan. A sees that a journal exists and compares J2's plan to J1's hashes, falsely refusing a recoverable state. If J2 has just been published and no member changed, A can unlink J2 as though it were J1. The initial existence check can also race with removal. Validate the current journal under the locks used for replay (retry on generation change and handle normal disappearance); make the single-primary rule an invariant of the interface rather than a docstring. Pin the J1→J2 and disappearance interleavings with deterministic tests, not sleeps.
2. **High · substance · T-02 (SC-01 / SC-02 / SC-05): expose the transaction outcome, not the journal path.** `plan.yaml:150` has the consumer infer whether anything committed from pathname existence after release. A second writer can recover the failed write before the catch checks, prompting the false message “nothing was written”; a distinct successor journal can also produce a false pending receipt. The core must distinguish pre-commit refusal from recoverable in-flight failure. Also, moving `relay_changed_state_feedback` outside the catch prevents rollback but a stderr exception (`harness_boundary.py:508–513`) still makes an already-committed CLI look failed before its `APPLIED` receipt. Define and test that post-commit outcome explicitly.
3. **High · substance · T-02 (SC-07): final verification omits three promised suites.** T-01 runs the observations, expertise and inflight-registry suites, and T-02 records a base run, but T-02's verify does not run them on the final tree. Both tasks contribute to SC-07; the terminal verify should cover every named suite, not infer the unedited assertions passed from a predecessor or baseline result.
4. **Med · substance · T-02 (SC-01): use a schema-valid feature.json mutation in case (e).** `plan.yaml:143` asks for an unrelated added top-level key, but the writer rejects unknown keys (`schemas/feature.json:6`, `feature_json_write.py:191–208`). Pin a known schema-valid change (e.g. increment existing `cycles_used`) and assert both that change and the recovered amendment. Confirm `_sign` succeeds where the fixture depends on a signature.
5. **Low · form · decision disposition.** Add DEC-230 `keep` for the INV-40 signed-task/judgement clause (`DECISIONS.md:7765–7768`): replay changes precisely how those amendment judgements land, while leaving the gate and hashes unchanged.
