## Findings

The authorized orchestrator's grant covers ordinary files in its assigned feature dir (`.harness/team-config.yaml:39–50`). A governed orchestrator can create a malformed file under an unreserved recovery name; the next ordinary plan amendment or feature-record update refuses at exit 5 before its transform, and keeps refusing until the file is removed. Other locked writes in that directory are also affected. The base has no journal discovery. The existing unit receipt corroborates that a differently named entry can refuse an unrelated same-directory write (`fix-c3-build/unit.txt:2534–2535`); governed Write reachability is a static trace, not a live bypass reproduction. Reconcile the recovery namespace with what the file-tool gate protects; keep the ruled handling for both canonical names.
2. **Medium · substance · T-01 · changed sidecar coverage; required hardlink route incomplete.** With the gate installed in main and no project-root override, OMP spawns the policy from its own extension root (`harness-hooks.ts:22–40,483–507,533–540`). `_hardlink_plan` scans only the gate root's feature directories (`check-domain.py:129–155,2506–2536`), not the target checkout's. If an existing journal in the assigned linked worktree has a same-worktree hardlink under an allowed note name, neither path spelling nor realpath identifies the journal, and the inode scan examines main instead. An orchestrator's Write can therefore reach the journal inode if the alias already exists and the write updates it in place. The fixture explicitly makes its feature dir and gate root coincide (`check_domain_support.py:36–51,111–115`). Static-only; unusual alias precondition. The scanner's anchoring predates the feature, but this journal and its claimed protection are new (`f4b1962e`, `fc69c032`). Anchor the ruled identity check to the destination checkout and cover a linked-worktree fixture with the gate rooted in main.
