# EFFICIENCY angle — FEAT-58-corpus-outside-worktree plan review

One finding, medium severity. Three of the four assigned questions resolve to "assessed,
not flagged" with measured evidence; the fourth (corpus_read batching) is the one real cost.

## Finding 1 — T-03: unbatched per-site `corpus_read` multiplies subprocess cost across 21 sweep sites

- **Anchor**: plan.yaml T-03 intent (lines 204–219); measured against `.claude/skills/harness/bin/check-state.sh` at HEAD, which has 21 `glob.glob(os.path.join(H, "*", "features", "*", ...))` sweep sites (T-03's own count, confirmed by grep), including **8 independent sites** that each separately re-glob and re-parse `feature.json` (lines 608, 1151/1225, 1312, 1341, 1576, 1615, 1726, 2030/2133/2176/2188, 2371 — several loops per feature), plus one each for `BRIEF.md`, `PLAN.md`, `plan.yaml` (loaded and also read as text), and `STATE.md`.
- **Measured**: `git show <ref>:<path>` in this repo, 30 real `feature.json` paths at `HEAD`: **13.69 ms/call** (411 ms / 30 calls). A batched `git cat-file --batch` over the same 30 paths, one process, one pipe: **17.4 ms total** — ~24× cheaper, ~0.58 ms/path amortized.
- **Cost**: T-03's intent resolves the *feature set* once (`corpus_root`/`corpus_features` called once — correct) but does not memoize or batch the *content* reads. Today those 8+ feature.json re-reads and the BRIEF/PLAN/plan.yaml/STATE.md reads are free (`open()` on a local file, sub-microsecond). Once T-03 routes each of them through `corpus_read` for the ~87 of 88 features that are unmaterialised in a sparse worktree, each becomes its own `git show` subprocess. At ~11 independent content-read call sites per feature × 87 unmaterialised features × 13.69 ms ≈ **13–14 seconds added latency to a single check-state.sh run** that is free today. This is exactly the plan-surface case the skill names: "the same file read repeatedly across sequential tasks where one pass could feed several" — here it's the same file read repeatedly across sweep *sites* within one task.
- **Alternative**: wrap `corpus_read` at the top of check-state.sh's python body (or inside `harness_boundary.py` itself) with an in-process cache keyed on `(path, ref)` — a plain dict or `functools.lru_cache` collapses the 8 independent `feature.json` reads per feature to 1. Better: since the resolved feature set is already known at the top of the file, do one `git cat-file --batch` pass over every corpus-relative path check-state.sh will need (feature.json, BRIEF.md, PLAN.md, plan.yaml, STATE.md for every unmaterialised feature) before any sweep runs, and serve every site from that dict. The measured 24× ratio applies directly.
- **Same root cause, lower measured stakes**: T-04's four validators (`board_lifecycle.py`, `check-plan-routes.py`, `validate-feature-json.py`, `layout_migration.py`) have 1, 4, 1, and 3 corpus-sweep sites respectively (grepped, not 21) — worst case ~4 sites × 88 features × 13.69 ms ≈ 4.8 s per validator, not per-feature-redundant like check-state.sh's 8-site feature.json case. Not filed as its own finding since the per-validator site count doesn't show internal redundancy the way check-state.sh's 8 feature.json sites do — but the same cache/batch fix, applied once in `harness_boundary.corpus_read` itself, would fix both for free and is the more durable home.
- **Severity**: med. Real, measured, bounded (~13–14 s, not minutes), on a script that is manual-only (see below) rather than a per-write hot path — a human waits on it once per invocation, not silently on every session tick.

## Assessed and explicitly NOT flagged

**Hot-path census** (`.claude/settings.json` read directly):
- `check-domain.sh` — PreToolUse `Write|Edit` **and** PostToolUse `Write|Edit|Bash`. The only genuinely hot script T-06 touches. T-06's added `corpus_root()`-based hardlink scan sits behind the pre-existing `st_nlink < 2` cheap gate (check-domain.sh :1913) — verified this gate is unconditional and ordinary (non-hardlinked) files have `st_nlink == 1`, so the expensive glob-at-corpus-root path is never reached on the common write. Confirmed by design, not a finding.
- `merge-gate.py` (T-05) — invoked by `merge-gate.sh` on *every* PreToolUse Bash call, but `main()` (merge-gate.py:161) returns before touching `feature_for`/`corpus_features` unless `github.get("sync")` is on **and** `merge_ref(command)` recognizes the command as an actual git/gh merge. Read the source directly: the corpus-sweep work T-05 changes only executes on real merge commands, which are rare relative to the Bash-call volume the wrapper script sees. Not a finding.
- `dispatch-guard.sh` (T-12) — PreToolUse `Task|Agent`, fires once per subagent dispatch, not per write. T-12's added check (matching two HARNESS-CORPUS-* lines against a plan's `corpus:` mapping) is a string comparison, not a corpus read — no cost concern.
- `check-state.sh` (T-03) — **not registered anywhere in `.claude/settings.json`**, confirmed by full-file read; it is manual-only (matches this repo's own Expertise G-01). The 13–14 s finding above is a real cost but it is not a hot-path cost — it is paid once when a human runs the gate, not on every session tick.
- T-04's four validators — confirmed via `.github/workflows/tests.yml` that `validate-feature-json.py`, `check-plan-routes.py`, and `layout_migration.py` each run exactly once per CI job (grepped their invocation lines directly); `board_lifecycle.py` runs once per feature at ship, per check-state.sh's own comment ("that runner now sits inside `ship`, once per feature"). None of the four are hot paths.

**`corpus_root()` recomputation** (T-01's "no cache, no module state" clause) — measured directly against the live `harness_boundary.py`: `worktree_owner()` 15.7 µs/call, `resolve_root()` 11.2 µs/call (2000-iteration loops, both pure `os.path`/file-read syscalls, no subprocess — confirmed by reading the source, which states and shows "NO GIT SUBPROCESS"). `corpus_root()` itself is on this order (tens of microseconds). This is noise against the several-millisecond cost of spawning the `python3` interpreter for the guard script itself, at any plausible call volume. Not waste.

**Test-run costs (T-07, T-08, T-09, T-11)** — measured fixture worktree creation directly: `git init` + one commit + `git worktree add --detach` against a throwaway two-file fixture repo took **77.8 ms**. Every worktree these four tasks create is built against a small fixture repo, never the real 88-feature corpus — T-08's "full pre-change worktree" for its red-first control is a fixture-scale full checkout, not a real-corpus one.
- T-07's seven-readers-times-two-fixture-trees parity matrix is required evidence for SC-09: it proves **seven distinct readers** (not one reader re-run) behave identically across a sparse and a materialised view. This is boundary evidence by the skill's own carve-out, not duplicated work.
- T-08's red-first control worktree and T-09's/T-11's fixture worktrees each target a different subject under test (the sparse-derivation script itself in T-08; the migration script's per-worktree order/refusal in T-09; `cmd_remove`'s post-sparsification dirty-gate discrimination in T-11) even though the "create a fixture worktree, then sparsify it" setup step looks similar across T-09 and T-11. At ~78 ms per worktree creation, the total duplicated setup across all four tasks is on the order of a few hundred milliseconds — not "minutes," and not worth collapsing into a shared fixture at the cost of coupling three independently-owned test files together.
