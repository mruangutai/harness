## Q1 — the orchestrator's hypothesis holds
Verified: `basePayload` is `{agent_type, hook_event_name, cwd}` (`.omp/extensions/harness-hooks.ts:220-222`); the Bash payload adds only `tool_name`/`tool_input` (`:686-690`); both primitives exist (`harness_boundary.py:150,:205`; `inflight_registry.py:316`). The probe's "unresolvable ≥2" verdict answered "WHICH one assignment?" — a question this rule never needs. Set membership refuses the measured B-10 incident (the main checkout is in no agent's S) and refuses the cross-persona sibling write, keeping my prior Q3 (sibling direction in scope) intact: one predicate still covers both directions.
What it gives up against exact-match — two residues, both same-persona collisions:
1. **False-allow:** a session of persona P dispatched for feature A writes into B's worktree while a concurrent P session holds B (single-flight is per `(feature, persona)`, DEC-204, so "one agent bound to A and B" is in practice two sessions of one persona). Allowed under set membership, refused under exact-match. Live topology: 3 personas hold ≥2 claims right now (probe §C).
2. **False-refuse:** P holds a worktree'd claim somewhere while a concurrent P claim for an un-worktree'd feature writes the main checkout — S is non-empty, so refused, though REQ-01 calls that session unbound. Rare (all six live features are worktree'd), loud, actionable per REQ-06, and fail-closed is REQ-05's own chosen direction.
ACCEPTABLE — a reasoned boundary, not risk acceptance: exact-match is UNBUILDABLE on Claude Code (no feature field on any write payload, no per-message hook to build a capture on — probe EXT §3, and DEC-110: persona is the whole write-payload identity), and on OMP buildable only by binding a refusal gate to `currentFeature` — untested (zero matches for `detectHarnessFeature|setFeature|captureFeatureFromMessage|featureCaptured` in `tests/unit/omp-hooks.test.ts`, verified), with a named wrong-feature-first branch (`harness-hooks.ts:619-621`) whose miscapture binds the guard to the WRONG worktree: refusing the agent's legitimate writes AND allowing the sibling harm, introduced by the key itself, plus an unresolved throw-in-async-handler host fate (`:598-602`). Set membership's inputs are durable disk state (git pointer files + persisted claims); it cannot misattribute — its false-allow slice requires a real live claim by the same persona at the destination, which is also the one place a stray write is caught by that flow's own orchestrator pen (DEC-153 sanction 2). Residue 1 is also NOT the measured incident class: B-10's mechanism is cwd-relative resolution into the MAIN checkout, which set membership closes completely. Exact-match may later be AND-ed on top on OMP once the capture mechanism is tested — a separate issue, not this plan.
RULING Q1: Set membership is SOUND and is the binding key (CLAIM-SET MEMBERSHIP); its two same-persona residues are accepted as a reasoned boundary forced by the identity available at the guard, and both MUST be stated in the plan's D-NN and the DECISIONS.md entry — ADVISOR'S TO MAKE (operator ratifies via the plan signature).

## Q3 — fail-open surface under the ruled key
- (a) No live claim anywhere: S empty → ALLOW. REQ-01's own scope. MUST test (SC-04 case 3 already covers it).
- (b) Claimed feature with no linked worktree: the claim lands in the MAIN checkout's registry (`dispatch-guard.sh` `_root_for` fallback), invisible to a fan-out over linked worktrees → S empty → ALLOW. Agrees with probe EXT §5 and my prior REQ-05 position. MUST test discriminatingly: an implementation that also scanned the main-checkout registry would silently flip this to refuse.
- (c) Unparsed `.git` pointer: destination checkout unresolvable while S is non-empty → REFUSE (REQ-05 bound-but-unplaceable; SC-05's existing treatment). An unparsed pointer met during the fan-out keeps that worktree OUT of S, so a write aimed there refuses by the same predicate — fail-closed, correct direction; fold into the same SC-05 fixture. MUST test the destination case.
- (d)/(e) Capture-timing and wrong-first-marker: MOOT — the ruled key never reads `currentFeature`. If a later issue adopts exact-match on OMP, (d) and (e) become mandatory tests THERE.
- PLUS one case the dispatch did not list, and the plan MUST test: **multi-claim membership ALLOW** — a persona holding live claims in ≥2 worktrees writes inside one of them, exit 0 on both routes. Without it, a fan-out that refuses on ≥2 candidates (the probe's cycle-1 reading) passes every other case in the suite.
Plan note for the PM: SC-05's "two prefix-matching candidates" fixture and REQ-05's "cannot be attributed to a single feature" clause are exact-match-era wording — under this key single-feature attribution is never required, so the ambiguity fixture must be restated in set-membership terms (unresolvable destination; unparsed pointer). Not a scope change: every refusal REQ-05 requires still refuses; the vacated branch refused only what this key resolves without guessing.
RULING Q3: (a) allow, (b) allow, (c) refuse; tests REQUIRED for (a), (b), (c-destination) and the multi-claim membership allow case; (d)/(e) not applicable to the ruled key — ADVISOR'S TO MAKE, extending the prior REQ-05 position.
