- 2026-08-26: T-14 design, the byte-vs-commit instruction is worth 5 false positives. Of 9 features whose pin resolves against plan.yaml, 5 (FEAT-21, 23, 24, 29, 30) have a pin that is NOT an ancestor of the last commit touching plan.yaml, yet the BYTES are identical - the later commits moved the file (FEAT-21 was the layout migration) without changing content. A commit-comparison reports all 5; the byte comparison reports none. The operator's constraint was right and is now measured, not assumed.
- 2026-08-26: T-14 design, the literal rule is 50% false-positive today. It produces exactly 2 findings: FEAT-41 (genuine content drift) and FEAT-27 (Done, PR 574) whose entire post-pin diff is an approval-amendment record plus one task flipping pending->done. Record-keeping after a review is normal and must not read as a false review claim. Scoping to non-terminal stations leaves exactly 2 features in scope tree-wide (FEAT-40 Review, FEAT-41 Plan) - a deliberately small surface that guards precisely the window where a pin's claim is load-bearing.
- 2026-08-26: T-14 design, the stated precondition is a LAGGING indicator and inverts the guard. "Any feature whose feature.json records a validator run" SKIPS FEAT-40, which sits at Review with a resolving, byte-current pin and NO validator run recorded. That is the exact window the check should protect: pin taken, pm still writing, panel not yet run. Gating on a recorded validator run means the check can only fire AFTER the panel has already read the wrong text. The precondition should be "a pin exists AND the station is non-terminal", not "a validator run is recorded".
