# FEAT-2452 simplify pass: SIMPLIFICATION angle on the plan draft. Six flag-only findings (1 med, 5 low), none blocking

**BLUF.** The plan's shapes pass the deletion test. `try_gh`/`GhResult`, `launch_gh`, `issue_number_from_url`, gh-sync's `gh`/`gh_try` policy wrappers and wayfind's local 404 helper each sit in front of more than one caller or carry a real policy, so deleting any of them would push complexity back out to the call sites. The complexity this plan adds is **restatement**: one rule written in several places that are already starting to say different things. The one med finding is the offline-gh confinement contract. It is spelled out three times (T-02, T-03, T-04) in wording that has already drifted, and the plan as written implements it separately at about a dozen fixture env sites. Everything below is FLAG-ONLY, and harness-pm applies it. I re-raise no settled ruling and no cycle-1 panel finding.

Scope read: `plan.yaml` (all lines, intents in full via raw read) and `BRIEF.md`. Code checked against plan claims: `factory_gh.py` (`_launch_gh`, `run_gh`, `GhError`, `_rate_limit_budget_error`, `create_ref`), `gh-sync.py` (`gh`, `gh_try`, `GH`), `gh_issues.py`, `gh_cost_log.py`, `factory_cli.py` docstring, `tests/harness_config_support.py`, and GH_SYNC_GH/gh_bin occurrences under `tests/`.

## Findings

1. **[med] The offline confinement rule is restated three times and implemented per fixture.** Tasks: T-02, T-03, T-04. SC: SC-02.
   - *File/line:* `plan.yaml` L242 (T-02: "separate directory holding an offline sentinel executable named gh that appends its argv to a sentinel log and exits 97 without network access; the FACTORY_GH fake lives outside that directory"), L264 (T-03: "logs its argv and exits 97 without network access"), L285 (T-04: "prepend an offline sentinel gh directory to PATH"; it says nothing about exit 97, a separate directory, or the fake living outside it).
   - *Cost:* SC-02's single-override proof depends on every fixture applying the same five-part contract: only FACTORY_GH is set, inherited GH_SYNC_GH is stripped, the sentinel goes first on PATH in its own directory, the sentinel exits non-zero, and the sentinel log is asserted empty. As planned, that contract gets hand-built in `gh_sync_support.run` plus the separate runners in test-factory-integration, test-factory-issue-types, test-gh-board `fake_gh`, test-board-lifecycle `_stub_env`, test-board-station `run` and test-wayfind. Thirteen files under `tests/` set GH_SYNC_GH today. A copy that leaves out one part, such as T-04's spelling, which drops the separate directory, still passes its own tests. That is the exact vacuous-confinement failure SC-02 is meant to rule out.
   - *Alternative:* Add one create-file to T-02's `files`, for example `tests/gh_offline_support.py` (`create: true`). It would expose one `offline_gh_env(fake, tmp)` returning the env dict plus the sentinel-log path, alongside an `assert_sentinel_unused(log)`. This follows the tree's own precedent: `tests/harness_config_support.py`, "THE one … fixture builder", lives at `tests/` root, which both unit and integration tests already put on `sys.path`. State the contract once in T-02. In T-03 L264 and T-04 L285, replace the restatement with "use T-02's `offline_gh_env` / `assert_sentinel_unused`; do not re-implement confinement". File ownership stays disjoint, because T-03 and T-04 only import the helper.

2. **[low] GhResult carries status/stdout/stderr that duplicate GhError's, and they already disagree for one path.** Tasks: T-01, T-04. SC: SC-01, SC-03.
   - *File/line:* `plan.yaml` L204 ("return error plus original captured streams/status") and L282 ("completed gh process with a nonzero integer status (never None, which is a launch failure)").
   - *Cost:* `GhError` already holds `argv/status/stdout/stderr` (`factory_gh.py` L107-111). `_rate_limit_budget_error` builds its GhError with `status None` after a *completed* non-zero process (L70-71, L84-85). Under the planned type, a rate-limited result therefore reports `result.status == 1` and `result.error.status is None` at the same time. T-04's rule "None is a launch failure" only holds if the helper reads `result.status`, and the plan never says which of the two to read. The outcome still fails closed, so this is a reader-load cost and not a defect. Even so, every consumer has to work out which of the two copies is authoritative.
   - *Alternative:* Add one sentence to T-01 L204: "GhResult.status/stdout/stderr are the authoritative process facts (status None only when launch failed). `error` carries the diagnosis; callers classify on the result fields, never on error.status." In T-04 L282, write "result.status" explicitly. Add no new field and no new test.
