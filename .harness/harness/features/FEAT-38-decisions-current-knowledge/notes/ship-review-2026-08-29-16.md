## The two things that matter most in this document

### 1. A reachable remote-code-execution hole was found, and fixed

The review panel found, and I reproduced myself before spending a cycle on it, that
`check-decision-claims.py`'s `{git, grep}` allowlist **did not bound execution**. A claim marker in
a markdown file reading

```
<!-- claim: git -c "alias.zz=!touch /tmp/p_f" zz :: nothing -->
```

executed its payload. The first token was `git`, so the allowlist passed it. Three git config keys
reach a shell this way (`alias.*`, `core.fsmonitor`, `diff.external`) and the next git release will
add more.

It was reachable from CI on every pull request. **The uncomfortable half, stated plainly: wiring the
checker to the live authority — which was the correct fix for a real gap earlier in this same
feature — is what turned a latent weakness into a CI-reachable one.** REQ-08 inherently executes
commands taken from a document, so the allowlist was the only thing between a markdown file and the
runner.

The fix bounds execution by **position and shape** rather than blacklisting config keys: option-like
tokens are refused in git's global-option position, git subcommands are allowlisted to read-only
ones, and ambient config is neutralised in the subprocess environment. I re-ran every vector myself
afterwards — all refused, payloads unexecuted — and the security reviewer then tried to get *past*
the new rules rather than re-running the known three, and could not. `severity_max` is now `med` and
nothing gates.

### 2. Three signed `verify:` blocks cannot pass as written — and this needs your signature
