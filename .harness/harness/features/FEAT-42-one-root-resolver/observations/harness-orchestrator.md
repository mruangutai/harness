# Observations - harness-orchestrator

- 2026-08-26 (FEAT-42 plan): dispatch async/sync behaviour is NOT stable within one orchestrator session. My first three dispatches to harness-product-lead each BLOCKED and returned the child's full digest; the fourth, issued identically, returned "Async agent launched" in ~2s with no result. Probe #746 frames this as a configuration question (CLAUDE_CODE_DISABLE_BACKGROUND_TASKS unset = async), but the variable did not change mid-session, so configuration alone does not explain the split. Consequence: never write a return that depends on a dispatch having come back — check for the completion notification, because the same call shape gives both behaviours.
- 2026-08-26 (FEAT-42 plan): an operator citation can overstate its own source. The ruling to scope harness-hooks.ts:144 in cited FEAT-40/observations/harness-orchestrator.md:58 as proof the defect "has already bitten". Reading the line: it describes the env-inheritance mechanism, then says verbatim "That reasoning was plausible and WRONG - the main-clone run fails too". It is a REJECTED explanation, not a casualty. The ruling still held on independent evidence (the verified :144 line plus a one-hit repo grep), so the correction cost nothing - but writing it into BRIEF unchecked would have put a false provenance in the permanent record. Read the cited line before propagating a citation, even the operator's.
- 2026-08-26 (FEAT-42 plan): FEAT-42's target defect demonstrated itself again, unprompted, in a file the plan already tasks. Running validate-feature-json.py with cwd set to the feature directory made it scan `<featuredir>/.harness/*/features/*/` and report "0 file(s)" - a clean, confident, entirely wrong answer, because validate-feature-json.py:40 resolves root from cwd with no marker check. Re-running with HARNESS_PROJECT_DIR set to the worktree root found 38. A validator that reports 0 files and exit 0 reads as PASS, which is the fail-open shape D-3's strict mode exists to kill. Lesson beyond this feature: when a checker reports ZERO findings, verify it looked at the right tree before believing it - zero is the value a misrouted scan returns.
