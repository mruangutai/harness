## Part 3 — the three attacked coverage claims

**SC-01b case-B short-circuit — real finding, not vacuous.** Corroborated the operator's
measurement (predicate raises `IsolationViolation` on all 5 trials, short-circuit never fires in
practice). Independent question answered: yes, it is a defect worth a finding. `committer_failed`
(test-feature-worktree.py:784) is set by a `BrokenBarrierError` timeout or ANY `OSError` from a
committer thread (lines 593, 607) — neither is inherently an isolation collision — and when it is
true, `case_shared_checkout_negative` (line 806) marks the case `detected` WITHOUT EVER calling
`assert_commit_isolation`. A run where a committer fails for an unrelated environmental reason
(disk pressure, a scheduling timeout) reports SC-01b's discriminating negative as PASS having
never exercised the one predicate that discriminates it. Finding #1, severity **med**.

**SC-01's static isolation assertions — confirmed unproven able to redden.** T-01's red proof
(`FEATURE_WORKTREE_BIN=/nonexistent/feature-worktree.py`) makes `run_cli` fail to invoke any
binary at all, failing the ENTIRE suite at once — this proves only "the suite requires a CLI to
exist," not that `case_isolation` (line 194, marker-file checks) or `case_branch_isolation`
(line 217, HEAD-name checks) themselves catch a genuine isolation bug (e.g. two worktrees
resolving to the same directory, or HEAD misreporting). Unlike T-04/T-05/T-06/T-08, which each
mutate one named flag/constant and re-run to show a specific reddening, T-01 never mutates
`feature-worktree.py`'s logic and reverifies against these two functions specifically. Confirmed
true: those assertions are green without independent proof they can go red. Finding #2, severity
**med**.

**`feature-worktree.py list`'s `commonpath` — gap confirmed, case named precisely.** `cmd_list`
(feature-worktree.py:170) correctly uses `os.path.commonpath([real_path, worktrees_root])`, which
rejects a sibling like `.claude/worktrees-old/<id>` (common prefix stops at `.claude`, not
`worktrees_root`) where a naive `real_path.startswith(worktrees_root)` would wrongly include it.
`case_list` in test-feature-worktree.py (lines ~285-303) only asserts the two genuinely-created
worktrees (FEAT-90, FEAT-91) appear correctly — no case ever creates a `worktrees-old` (or any
prefix-colliding) sibling directory and asserts `list` excludes it. Confirmed: a `startswith`
refactor of line 170 would pass the whole suite unchanged. Finding #3, severity **med**. Missing
case: in `case_list`'s fixture, create a real git worktree at
`<owner_root>/.claude/worktrees-old/<id>` (or any sibling sharing `worktrees_root` as a string
prefix but not as a path component) and assert its path is absent from `cmd_list`'s output.
