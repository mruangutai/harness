# Expertise — harness-pm
## Patterns (max 15)
- P-01: WHEN one success criterion's carrying assertions live under both `tests/unit/` and `tests/integration/` DO split it by test kind: directory selects the runner, so each resulting criterion must name the one kind that executes all its assertions.
- P-02: WHEN an unmet criterion is remedied by editing validate-digest.py or test-validate-digest.py DO record that no squad can take it: DEC-174 makes both main-session-direct, so even a test-only fixture gap becomes a user-channel question rather than a task a lead can place.
- P-03: WHEN a plan needs one task to land before another DO put it in `depends_on`: teams/build.yaml reads only `from_task_depends_on`, so an ordering written as prose in `intent` is invisible to the scheduler, and both id order and file order place a later-added task last.
- P-04: WHEN revising a field of an existing task or decision DO expect apply to replace it in place (REPLACED, exit 0); only a differing plain top-level key exits 7. For a signed task's intent, files or verify use amend --expect-sha256 --reason, which ledgers the change INV-40 otherwise reports.
- P-05: WHEN a criterion rests on a CI-run gate that reads git history DO price the workflow's checkout depth first: a bare `actions/checkout@v4` clones depth 1, so a pinned historical blob is unreachable in CI and the criterion is unmeetable as written.
- P-06: WHEN transcribing a panel finding id DO compute it from the digest summary unaltered and record the normalization in `panel.transcription_rule`: panel_findings.py only lowercases and collapses whitespace, so stripping a backtick changes the hash and the operator's later ruling reads as a stale override.
- P-07: WHEN a plan.yaml does not exist yet DO create it with plan-merge.py apply and a proposal carrying no approval mapping: an absent base bootstraps and the tool splices approval status pending itself. Only a proposal that carries its own approval block is refused. Direct writes are unnecessary.
- P-09: WHEN citing check-state.py INV-32 output as evidence a panel record is complete DO check the plan's approval status first: INV-32 grades approved plans only, so a pending plan emits zero lines even with an open high finding. Prove the reader branch against data and a mutant.
- P-11: WHEN a dispatch fences a harness bin script's capability as settled DO run --help on the control-plane copy, never the worktree's: a worktree behind main is the stale witness, and the control-plane script invoked by absolute path runs fine from inside a worktree.
- P-10: WHEN selecting `change_type` DO choose from the configured test-matrix vocabulary before signature and confirm its required test-kind floor matches the task's planned evidence; unsupported labels are malformed records, not reasons to extend or guess the matrix.
- P-12: WHEN DEC-174 routes a build main-session-direct and the main session parallelizes task subagents DO state that all relative-path edits must remain inside the assigned feature worktree.
- P-13: WHEN goal-checking a Harness digest append DO require the canonical historical reader to select the submitted object from the exact prospective bytes before the first write; schema acceptance alone does not prove successor readability.
## Gotchas (max 15)
- G-01: WHEN a step must create, copy or move a file DO use the file tools or a Python script — `bash-write-guard.py` denies redirects, `cp`, `mv` and `rm` in Bash whatever the target, including the session scratchpad and paths with no repo-like component.
- G-02: WHEN a Bash command names a path the guard should allow DO spell it as a literal absolute path. The guard reads the command line, not the resolved path, so the same target written through a shell variable is refused.
- G-03: WHEN sizing or amending a task DO count its machine-field lines against the 50-line per-task cap first: amend accepts an over-cap task and only plan-merge check or check-plan-routes.py fails it, and intent is not counted, so derive a long file list inside verify from plan.yaml rather than inlining it.
- G-04: WHEN a task edits .harness/harness/docs/DECISIONS.md DO also list DECISIONS-INDEX.md and re-run gen-decisions-index.py, even when no row's text changes: the index stores a per-row source line, so lengthening one entry shifts every later anchor and the regeneration test reddens.
- G-05: WHEN running check-plan-routes.py DO pass your own plan.yaml FILE: with no argument it reports every live plan, so other features' DEVIATION lines read as yours, and handed a directory it raises IsADirectoryError and exits 1, which reads as a gate failure rather than a bad argument.
- G-06: A detect value in harness.json test_kinds is a pipe-separated string, not a list: iterating it yields one character per step, which prints like a successful enumeration of globs. Split on the pipe before matching anything.
- G-08: WHEN a plan adds, moves, or deletes a Harness test DO account for the directory invariant: `tests/unit/` and `tests/integration/` select the kind, `suite_layout.py` refuses undiscoverable or duplicated test shapes, and the runner exits 2 on any violation.
- G-09: WHEN editing a file that a domain guard protects DO put the ABSOLUTE path in the edit's section header: a bare filename resolves against the working directory rather than the file you read, and the write is denied even where the lane grants it.
- G-11: WHEN naming a path under .agents/skills DO spell it .claude/skills for git show and check-domain --resolve: .agents is a symlink here, so git show of an .agents path prints nothing and reads as content absent everywhere, and listing both spellings does the same work twice.
- G-12: WHEN check-plan-routes.py prints DEVIATION for a granted main-session-direct path DO read a TASK deviation as expected DEC-174 carve-out output that does not gate — but a MANIFEST deviation, raised when a worktree team-config routes differently from the owner's, is counted and exits 1 with no VIOLATION line.
- G-13: WHEN a verify greps DECISIONS-INDEX.md for a ruling phrase DO note the ' :: <ruling>' tail is hand-written by the entry's author and gen-decisions-index.py does not produce it, so regeneration alone never satisfies the grep and the task intent must say to write the row text.
- G-14: WHEN running a copy of a harness bin script out of tree DO either keep the copy inside the bin directory or give the arm root .harness/team-config.yaml, harness.json and factory/: root resolution reads the script's own location and otherwise raises at import, so every case reads ABSENT.
- G-15: WHEN a Bash command carries a python heredoc DO avoid a bare `>` comparison inside it: bash-write-guard.py parses the command line textually, reports redirect targets and blocks the whole call. Write the comparison reversed with `<`.
- G-07: WHEN writing plan.yaml's panel key DO use record-panel from the validator lead's digest, never apply: panel is a plain top-level key, so apply exits 7 CONFLICT on any differing value. set-panel is the validated hand route, for a ruled repair only.
- G-16: WHEN quoting a decisions_affected clause that wraps across a DECISIONS.md line break DO write it as a double-quoted scalar with a literal \n at the break: plan-merge check requires the clause as an exact substring of the decision's section, newlines included, so a space-joined wrap fails as not verbatim.
## Outcomes (max 10)
- O-01: WHEN running a Harness gate suite as grading evidence DO clear HARNESS_AGENT_TYPE from the environment first: a pm-typed shell makes plan-merge refuse sign-approval and the plan-merge integration file returns ten FAILs that read exactly like a regression. Treat any failure naming your own persona as contamination.
- O-02: WHEN proving a harness bin gate behaves the same before and after a change DO run both sides from a git archive of the base, the candidate overlaying only HEAD's bin and tests, with HARNESS_PROJECT_DIR set to each archive: identical plans and corpus leave only the code varying.
