<objective>
Run the full harness on Sub-Phase B of the Implentio PDF editor — the annotation UI (split-screen PDF viewer + annotation form).

Purpose: Sub-Phase B is the UI-heavy sub-phase. It introduces an annotation API (architectural keywords: `API`, `interface`), a split-screen layout, and a form that submits corrections. This sub-phase tests the harness on a UI plan, where TDD is harder (components instead of pure functions) and the QA reviewer must review UI spec rather than backend logic. Screenshots of the UI will be provided at the discuss session.

Output: Evidence artifacts proving the harness was active across all stages. Special emphasis on: scope creep detection (re-parse logic belongs in Sub-Phase C — must be deferred), and QA reviewer handling UI test cases.

EXECUTOR NOTE: YOU ARE THE HUMAN (the CTO). Initiate each step. Claude agents assist at each stage.
</objective>

1. Sub-Phase A is complete and shipped.
2. Confidence scoring + data blocking logic is in the Implentio codebase.

NOTE: Sub-Phase B depends on the annotation API shape established in Sub-Phase A (the human review queue endpoint). The discuss session for Sub-Phase B must confirm what data the annotation form submits and how it connects to the Sub-Phase A queue.

### Stage 2: Discuss Phase

**Command:** `/gsd-discuss-phase [sub-phase-B-number]`

**Attach screenshots** of the annotation UI layout at the start of the discuss session.

**What to decide during discuss:**
- PDF viewer: which library? (react-pdf, pdfjs-dist, or iframe embed — each has tradeoffs)
- Layout: CSS approach for split-screen (CSS Grid, Flexbox, sidebar panels?)
- Annotation form fields: which extracted fields can be corrected? (all 6 from D-01, or subset?)
- Submission: what happens after the user submits an annotation? (triggers re-parse, or queues for batch?)
- API endpoint shape: POST /api/annotations or POST /api/queue/:id/annotate?
- Auth: who can annotate? (support team role — is there a role check on this endpoint?)

**Scope creep to catch:** If re-parse, re-scoring, or unblock logic comes up during discuss — push it to Sub-Phase C. The annotation form submits corrections; re-parse happens after submission, which is Sub-Phase C scope.

### Stage 4: Plan Phase

**Command:** `/gsd-plan-phase [sub-phase-B-number]`

**What good plans look like for Sub-Phase B:**
- UI components are harder to TDD with pure unit tests — plans should identify where vitest component tests or playwright tests apply
- The annotation API endpoint (POST submission) is TDD-eligible as a pure unit (validate request → update record → return)
- Plans should separate: PDF viewer integration, annotation form component, and annotation API endpoint
- No plan should touch re-parse or re-score logic (deferred to Sub-Phase C)
